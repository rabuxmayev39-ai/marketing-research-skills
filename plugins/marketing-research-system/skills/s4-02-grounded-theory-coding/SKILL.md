# Grounded theory coding: open, axial, selective coding and constant comparison (S4-02)

Grounded theory is a way of building an explanation (a "theory" in the modest sense of a set of linked concepts) from data, instead of testing one brought in from outside. Barney Glaser and Anselm Strauss introduced it in The Discovery of Grounded Theory (1967), together with the constant comparative method. Strauss and Juliet Corbin later set out the three coding steps used here: open coding breaks the data into concepts, axial coding relates categories to each other, selective coding integrates everything around one core category. A marketing team uses it to explain a process, for example how a buyer comes to switch supplier.

Evidence grade: A. Grades are A = tested in peer-reviewed research, B = established professional standard, C = practitioner tool with little formal testing. The method has decades of use and debate in peer-reviewed research. Two cautions on weight. First, its founders split and three versions now exist (Glaser's classic, Strauss and Corbin's, Charmaz's constructivist), so always say which one was followed; this skill follows Strauss and Corbin. Second, Timmermans and Tavory (2012) argue that pure induction rarely produces new theory and that the label is often used for any coding. A grounded theory from one small project is a well-argued hypothesis, not a proven model.

Working rules for the assistant: answer in the user's language (Uzbek, Russian or English). Label FACT (incidents and quotes with IDs) versus INTERPRETATION (codes, categories, relationships, the core category). When the model is written up, return to the research-orchestrator skill.

## When to use it / When not to use it
Use it when:
- The question is about a process or sequence: how people come to decide, switch, trust, or give up.
- No existing model fits, or the team suspects the standard model is wrong for this market.
- More data can still be collected, so that sampling can follow the analysis.

Do not use it when:
- The team only needs a description of patterns (S4-01) or a comparison across segments (S4-05).
- Data collection is finished and cannot be extended. Open and axial coding can still be borrowed, but do not call the result grounded theory.
- There is a strong prior theory to work against (S4-03), or time allows one pass only. The sources describe the method as time and resource heavy.

## What you need before starting (inputs)
1. A research question about a process, stated openly ("How do bakers come to change flour supplier?").
2. The first few transcripts or field notes, in the original language, with respondent IDs and profile.
3. Agreement that further interviews are possible and that who is interviewed next may change (theoretical sampling).
4. A memo file with dated entries, starting with a note of what the team already believes about the topic, so these beliefs can be watched during coding.

## Procedure
1. Set up. Ask the user: "What process are we trying to explain, and can we add interviews as we go?" If no further data are possible, say so in the report and treat steps 6-7 as limited.
2. Start analysis after the first two or three interviews; do not wait for the full set. Collection and analysis run together, and the method is iterative, not linear.
3. Open coding. Go line by line. For each incident ask who, what, where, when, how, and what is happening here. Give it a short code. Prefer codes for actions, phrased as gerunds ("checking the dough", "waiting for credit"), and keep striking respondent phrases as in vivo codes. Generate many codes at this stage.
4. Constant comparison. This runs through every step. Compare each new incident with earlier incidents under the same code; compare codes with codes; later, categories with categories. For each comparison record: same as before, a variation, or something new. Group similar codes into categories. For each category list its properties (shared characteristics) and dimensions (the range a property varies along, for example trust: low to high).
5. Memo throughout. After each coding session write a dated memo: what a category seems to mean, a hunch about a relationship, a gap, a decision and its reason. Memos are the audit trail; one source calls them the mortar between the data blocks.
6. Theoretical sampling. Use the memos to decide what data to collect next: who or what would fill a gap, test a hunch, or show a category under different conditions. Ask the user to recruit accordingly. This is sampling to develop categories, not to represent a population; do not describe it as representative.
7. Axial coding. Take one category at a time and relate the others to it using Strauss and Corbin's paradigm: conditions (what leads to it or surrounds it), actions and interactions (what people do about it), consequences (what follows). Write each link as a statement and check it against the data: list the incidents that support it and those that do not. A link with no supporting incidents is dropped; a link with contradicting incidents is narrowed by stating the conditions under which it holds (working rule).
8. Selective coding. Choose the core category: the one the other categories relate to and that explains most of what is going on. Write the storyline, a short narrative that connects every major category to the core. Writing it usually exposes gaps; return to the data or the field to fill them.
9. Judge saturation. Stop collecting when new data add nothing further to the categories and their properties are sufficiently explained. Report it per category and say on what basis it was judged (S2-04). If the project ended before that, say "not saturated" for the categories concerned.
10. Present the result as linked concepts, not as a list of themes: core category, the other categories, the statements linking them, the conditions under which the links vary, and the cases that do not fit. Then return to research-orchestrator.

## Worked example
INVENTED EXAMPLE - not real data. A flour mill wants to explain how small bakeries (novvoyxona) come to change flour supplier. Nine interviews, the last three chosen by theoretical sampling.
Input (open coding of two lines):
```
B2: "Yangi qopni ochsam, xamir boshqacha chiqdi, nonni qaytarib berishdi."   FACT
    codes: noticing the dough change | customers returning bread
B5: "Я не меняю, пока мне дают в долг до конца недели."                      FACT
    codes: staying for credit | weekly settling
```
Output:
```
Categories: batch inconsistency (property: frequency, rare-often) |
  credit tie | test baking | neighbour advice | quiet switching
Memo 14.03: bakers with credit complain but stay -> interview cash payers.
Axial, around "quiet switching":
  conditions: repeated batch inconsistency + no credit tie
  actions: test-bake one sack from a rival, ask a neighbour baker
  consequences: split orders for weeks, then drop old supplier
Core category: "protecting the day's bake"                          INTERP
Storyline: bakers act to protect each day's bread; supplier loyalty
  holds only while credit outweighs the risk of a bad batch.
Does not fit: B8 switched for price alone, no quality issue.        FACT
Saturation: "credit tie" judged saturated; "neighbour advice" not.
```

## Common mistakes
- Calling any coded interview study "grounded theory", or collecting all data first and coding afterwards with no theoretical sampling.
- Skipping constant comparison, which leaves the result descriptive.
- Reporting themes instead of interrelated categories around a core.
- Thin or missing memos, so nobody can trace how the model was reached.
- Forcing data into the conditions-actions-consequences frame when they do not fit (working rule). Glaser published a rebuttal of Strauss and Corbin's version, and Charmaz warns that theoretical coding can give a false sense of objectivity.
- Pretending the team had no prior ideas, or not saying which version of grounded theory was used.

## Quality checklist
- Did analysis begin while data were still being collected?
- Were later respondents chosen because of gaps or hunches in the analysis?
- Does each category have stated properties and dimensions, with incidents attached?
- Is each relationship written as a statement with supporting and non-fitting incidents?
- Is there one core category and a storyline linking the others to it?
- Are dated memos available, and is saturation reported per category with the basis for the judgement?
- Does the report name the version followed and present the model as a hypothesis?

## Works with
- S1-04 in-depth interviews and S1-07 JTBD switch interviews: the main data sources; switch interviews suit process questions.
- S2-04 saturation: the stopping rule in step 9. S4-04 coding cycles: in vivo and process coding for open coding; Saldana lists axial and theoretical coding as second-cycle methods.
- S4-03 abductive analysis: the alternative when existing theories should be used openly.
- S4-07 negative case analysis: for incidents that do not fit a relationship. S4-01 thematic analysis: use instead if only patterns are needed.
- S5-05 what would have to be true: to turn the model into testable conditions. S5-14 member checking: to put the storyline to respondents.

## Notes for Uzbekistan
- Code in the original language. In vivo codes stay in Uzbek or Russian exactly as said, with a working translation in brackets for mixed-language teams. Gerund codes are easy in English but awkward in translation. Use the natural verbal noun in Uzbek (-ish) or Russian and keep one convention across coders.
- Polite or agreeing answers hide the conditions under which people act differently. Ask for the last concrete episode, and in constant comparison weigh described episodes above general statements.
- Use theoretical sampling to cross the Tashkent and regions line on purpose: if a category was built only from Tashkent respondents, the next interviews go to a region.
- Do not recruit for theoretical sampling only through a Telegram bot; older and rural respondents are likely to be missed. Most published grounded theories come from Western health and social research. Do not import their categories; treat any resemblance as a hypothesis.
