# Matrix displays and framework analysis (S4-05)

A matrix display puts qualitative data into a table so the whole dataset can be seen in one place. Matthew Miles and Michael Huberman (later with Johnny Saldana) made displays one of three linked parts of analysis: condensing the data, displaying them, and drawing and verifying conclusions. The Framework Method is the best-documented version: Jane Ritchie and Liz Spencer developed it in the late 1980s at the UK's National Centre for Social Research for applied policy studies. Its defining feature is a matrix with one row per case (usually a respondent), one column per code or category, and a short summary of that respondent's data in each cell. Gale and colleagues (2013) describe it in seven stages for mixed teams.

Evidence grade: B. Grades are A = tested in peer-reviewed research, B = established professional standard, C = practitioner tool with little formal testing. This is a long-established professional procedure, widely used in applied policy and health research and described in open-access methodology papers. It gives order and an audit trail; it does not produce the interpretation. Gale et al. stress that the matrix still has to be read by someone skilled in qualitative analysis. Trust the matrix as a faithful map of the data if the checks below pass; treat conclusions read from it as interpretation.

Working rules for the assistant: answer in the user's language (Uzbek, Russian or English). Label FACT (cell summaries and quotes, traceable to a transcript) versus INTERPRETATION (patterns, typologies, explanations). When the matrix and its reading are delivered, return to the research-orchestrator skill.

## When to use it / When not to use it
Use it when:
- The data are semi-structured interviews or similar texts that cover broadly the same topics.
- Comparing across respondents and within each respondent matters for the question (segments, roles, cities).
- Several people analyse together, some without qualitative experience, or the dataset is large.
- The client wants to see how conclusions trace back to respondents.

Do not use it when:
- The data are very mixed and do not share topics.
- The question is about how a story unfolds, how talk is organised, or language itself. Gale et al. point to narrative, conversation and discourse analysis for those.
- The team wants a quick or "easy" route. The source describes the method as time-consuming and warns against treating it as a shortcut.
- The aim is to count how many people said something. Gale et al. warn that the spreadsheet tempts teams to quantify and that such counts mean little with purposive samples.

## What you need before starting (inputs)
1. Research question and the comparisons that matter (for example new versus long-standing customers).
2. Verbatim transcripts in the original language, with line or paragraph numbers and respondent IDs.
3. Respondent attributes: segment, role, city, channel.
4. A spreadsheet, and any topics fixed in advance by the brief (for deductive codes).
5. A lead with qualitative experience, and at least two people for the first coding round if possible.
6. Realistic time. Gale et al. estimate about half a day of charting per one-hour transcript for a practised team.

## Procedure
1. Confirm fit. Ask the user: "Do the interviews cover roughly the same topics, and which groups do we need to compare?" If topics differ widely between interviews, switch to S4-01.
2. Stage 1, transcription. Verbatim, readable, numbered. Pauses and speech detail are not needed for this method.
3. Stage 2, familiarisation. Read each transcript or listen to the recording, with field notes. Note first impressions in the margin.
4. Stage 3, coding. Code the first few transcripts line by line. Two researchers should do this independently if feasible. Codes may label content, values, emotions or notes on method. Even when the brief supplies codes in advance, do some open coding on a few transcripts so that unexpected material is not lost.
5. Stage 4, develop the working analytical framework. Coders meet, compare codes, agree a set, group codes into categories and write a short definition for each. Add an "other" code under every category. Expect several rounds before the framework settles.
6. Stage 5, apply the framework (indexing). Apply the agreed codes to all remaining transcripts, using short labels or numbers. When "other" fills up or a code does not fit, revise the framework and re-index the affected transcripts. Software can store and retrieve data; it does not do the analysis.
7. Stage 6, charting. Build the matrix: rows are respondents, columns are codes within a category, with attribute columns at the left. In each cell write a brief summary of what that respondent said on that code, keeping their wording and meaning where possible, with a reference to the transcript location and any quote worth keeping. Agree abbreviations and a charting style before starting. Working rules: mark "not asked" and "asked, nothing said" differently, because an empty cell is information; put the analyst's comments in a separate column, never inside the summary.
8. Stage 7, interpreting. Read down each column for the range of views on one topic; read across each row for one respondent's logic; sort rows by an attribute and reread. Write analytic memos. Use tactics listed by Miles and Huberman for generating meaning: note patterns, cluster cases, make contrasts and comparisons. Typologies and explanations are built here. Plan time for it: Gale et al. note this stage usually takes longer than planned.
9. Verify. Miles and Huberman treat verification as part of analysis. For each conclusion: check it against the full transcripts, not only the cells; look for outliers and extreme cases and use them to refine the claim; follow up surprises; compare sources where there are several; ask which rival account would fit as well. Drop or narrow conclusions that fail.
10. Derive further displays if useful: a matrix of segment by theme, a checklist matrix (present, absent, rating), or a time-ordered matrix. Each must trace back to the respondent-level matrix.
11. Report with the framework, the matrix (anonymised), the patterns with their evidence, exceptions, and limits. Describe spread in words ("most long-standing buyers", "two of the regional dealers") and avoid percentages. Then return to research-orchestrator.

## Common mistakes
- Using the interview guide questions as the framework and never revising it, or one person building it alone when a team was available.
- Charting before the framework is stable, then not re-indexing after changes.
- Pasting long quotes into cells so the matrix cannot be scanned, or summarising so hard that the respondent's meaning is lost.
- Mixing the analyst's interpretation into cell summaries, or leaving blanks unexplained.
- Counting cells and reporting percentages from a purposive sample.
- Stopping at the filled matrix: a completed chart is organised data, not a finding.
- Reading only down the columns and never across a respondent's row; underestimating the time for charting and interpretation.

## Quality checklist
- Do the interviews share enough topics for a common framework?
- Was open coding done on the first transcripts, by two people where feasible?
- Does every code and category have a written definition, plus an "other" code?
- Is every cell a short summary with a transcript reference, and are empty cells distinguished (not asked versus nothing said)?
- Was the matrix read both down the columns and across the rows, and by attribute group?
- Was each conclusion checked against full transcripts and outliers?
- Does the report avoid presenting counts as representative?

## Output template
```
FRAMEWORK ANALYSIS REPORT - [project] - [date]
Research question: ... | Comparisons needed: ...
Data: [n] transcripts | attributes | languages | lead and first coders
ANALYTICAL FRAMEWORK (version [n])
Category | code | definition | (each category ends with "other")
MATRIX (one sheet per category)
ID | attributes | code 1 | code 2 | ... | analyst notes
Cell = short summary + (page/line) + "key quote" in original language
Blank codes: NA = not asked | NS = asked, nothing said
READING THE MATRIX
Pattern | columns and rows it rests on [FACT] | reading [INTERPRETATION]
Typology or groups of cases: ...
Outliers and how they changed the claim: ... | Rival explanations: ...
Limits: sample, missing groups, framework changes made
```

## Works with
- S1-04 in-depth interviews and S1-07 JTBD switch interviews: semi-structured data suit the matrix. S3-11 interview snapshot helps familiarisation.
- S4-04 coding cycles: code types for stage 3; pattern codes can serve as columns.
- S4-01 thematic analysis: Braun and Clarke class framework as a codebook approach; use S4-01 when themes must be developed freely by one analyst. S4-03 abductive analysis: take exceptions and unexpected cells there.
- S4-07 negative case analysis: for the outliers in step 9. S2-07 triangulation: when the matrix combines several sources. S4-21 content analysis: use instead if counting categories is the real aim.
- S5-01 affinity diagram, S5-02 insight ladder, S5-03 insight tests: take patterns forward. S5-14 member checking: return summaries to respondents.

## Notes for Uzbekistan
- Keep key quotes in cells in the original Uzbek or Russian. Write summaries in the team's shared working language and agree that language before charting. Add columns for interview language and place (Tashkent or region) and sort by them before concluding anything across the whole sample.
- Polite or agreeing answers: where a respondent approved without giving an example, chart it as "general approval, no example" so it is not read later as support.
- If rows come from a Telegram-bot survey with open answers, cells will be thin and the rows are likely to miss older and rural people. Say so in the limits and do not compare them directly with interview rows.
- With an owner-led client who knows the dealers or customers personally, anonymise IDs and remove identifying details from cells before sharing the matrix. The method was developed in UK policy and health research. It is a way of organising data and transfers easily, but any typology borrowed from that literature is a hypothesis here.
