# Own case studies (S8-08)

Own case studies is the agency's internal library of finished projects, kept in the Case-Studies folder in one fixed format and consulted at every stage of new work. It is not a published methodology with a single author. It is an internal practice that borrows from three places: lessons-learned systems in large organisations, case-study research, and evidence hierarchies, which rank kinds of evidence by how well they guard against bias. The division of work with S7-04 is strict: the project retrospective (S7-04) writes one case file when a project ends; this skill defines the file format, stores and indexes the files, searches them before new projects, protects client confidentiality, and sets the rule for how much weight a few cases can carry.

Evidence grade: Local. In this index the grades are A = tested in peer-reviewed research, B = established professional standard, C = practitioner tool with little formal testing; "Local" is a separate label for the agency's own evidence. Its strength is fit: the cases come from this market, these channels, these languages and this team, which no foreign study offers. Its weakness is number and design: there are few cases so far, they were not chosen at random, there is usually no comparison group, and the people who wrote them took part in the work. The Center for Evidence-Based Management places case studies low for showing cause and effect, while noting they are a strong design for understanding why or how something happened and in what circumstances. Flyvbjerg (2006) argues that cases are undervalued and that a field needs well-described examples. Both points are used here. The governing rule: a handful of cases is a source of hypotheses and planning ranges, not proof. A known practical risk also applies: a US audit of NASA's lessons database (GAO, 2002) found that many managers did not use it, because relevant lessons were hard to find and people were reluctant to record negative ones. So mistakes must be recorded as carefully as wins, and files must be easy to search.

Working rules for the assistant: answer in the user's language (Uzbek, Russian or English). Label FACT (what a case file records, with its code) versus INTERPRETATION (what it may mean for the new project). Always state how many cases a statement rests on. Never reveal one client's confidential data to another. When the search or the filing is done, return to the research-orchestrator skill.

## When to use it / When not to use it
Use it when:
- A new project starts: search before the brief is fixed.
- A stage needs a planning number (response rate, cost per interview, time needed) and no published local figure exists.
- A retrospective has just produced a case file that must be filed and indexed.
- A Western rule is being adapted (S8-01 to S8-03) and the team asks whether it has seen the rule hold or fail locally.

Do not use it when:
- The team wants proof that an approach works. Cases suggest; tests (S7-02) and larger data show.
- The only similar case is from a different category, audience and channel. Say that no close case exists.
- Using the case would expose a client's confidential information.

## What you need before starting (inputs)
1. The Case-Studies folder and its index (one row per case).
2. For filing: the retrospective output from S7-04 and the project's final numbers.
3. For searching: the new project's decision, category, audience, place, channel and planned methods.
4. The confidentiality terms of each past client contract.

## Procedure
Part A - filing a case (after S7-04)
1. Give the case a code (Working rule: year, running number, category, for example 2026-07-FOOD) and use the code, not the client's name, in the file name and the index.
2. Write the file in seven fixed fields:
   - Decision: what the client had to decide.
   - What was expected: targets and the hypotheses written beforehand (S2-11).
   - Method: what was done, sample, dates, cost.
   - What happened: results against expectations.
   - Numbers: reusable figures with units and how each was measured.
   - Mistakes: errors, near-misses and what was luck.
   - What transfers: lessons stated as hypotheses, each with the conditions under which it was seen.
3. Anonymise. Working rules: replace the client and brand names with a generic description (a juice brand, a housing developer); remove names, phone numbers and usernames of respondents and staff; give money figures as ranges or ratios if the contract requires; keep the key linking codes to clients in a separate restricted file. If a small market makes the client recognisable from details alone, blur the details. Follow S2-10 and the client contract, and check the personal data rules in force.
4. Tag the index row: category, B2B or consumer, audience, place (Tashkent, region), language, channel, methods by ID, outcome (met, missed, mixed), date. Tag failed and stopped projects in the same way as successful ones.
Part B - searching before and during a new project
5. Search the index by category, audience, place, channel and method. Read every matching file, including failures. Working rule: a case is "close" if it matches on at least three of these five tags.
6. Extract into a table: case code, what matched, the relevant number or lesson, and the conditions. Put conflicting cases side by side; do not average them away.
7. Weigh the evidence. Working rules: one or two close cases give an idea to check; three or more close cases that agree give a working hypothesis and a planning range (lowest to highest observed), never a single precise figure. Look for a case that contradicts the pattern (S4-07) and for an outside source that confirms or disputes it (S2-07).
8. Write the result into the facts, assumptions, unknowns register (S0-13) as assumptions with the case codes, and plan a check for any that the decision depends on.
9. Report to the team with the number of cases stated in the sentence, for example "in 3 of our 9 filed cases". Return to research-orchestrator.
10. Upkeep. Working rule: twice a year, reread the index, merge duplicate lessons, mark lessons later contradicted, and note which lessons were actually reused.

## Worked example
INVENTED EXAMPLE - not real data. A juice brand needs a Telegram-bot survey with 600 completed answers. The library holds 9 case files; 3 are close (bot survey, consumer, food and drink).

```
CASE CODE      INVITATIONS   COMPLETES   RATE   NOTE FROM "MISTAKES"
2025-03-FOOD   5,000         400         8%     no reminder message sent
2025-11-FOOD   3,000         210         7%     survey took 14 minutes; many quit
2026-04-DRNK   4,000         360         9%     prize draw; 6% duplicates removed
Together       12,000        970         8.1%
PLANNING HYPOTHESIS (INTERPRETATION, 3 cases): completion rate 7% to 9%
Invitations needed for 600 completes: 600 / 0.09 = 6,667 (best case)
                                      600 / 0.07 = 8,572 (cautious case)
Plan for 8,600 invitations; keep the survey under 10 minutes; send one reminder;
check duplicates (S3-09). Not proof: 3 cases, different audiences and
seasons. Review the rate after the first 1,000 invitations.
```
Arithmetic check: 400 / 5,000 = 0.08; 210 / 3,000 = 0.07; 360 / 4,000 = 0.09; 5,000 + 3,000 + 4,000 = 12,000; 400 + 210 + 360 = 970; 970 / 12,000 = 0.0808; 600 / 0.09 = 6,666.7, rounded up to 6,667; 600 / 0.07 = 8,571.4, rounded up to 8,572; 8,600 x 0.07 = 602, which is at least 600.

## Common mistakes
- Filing only successes, so the library teaches that everything works.
- Treating three cases as a law, or quoting one case's number as "the" local benchmark.
- Free-form files that cannot be compared or searched.
- Client names and respondent details left in files that other teams or clients may see.
- Lessons written without conditions ("reminders work") instead of "seen in two bot surveys of urban buyers".
- Searching only at kickoff and not again when choosing methods, sizing samples or planning media.
- Using an old case without checking whether the channel or audience has changed since.

## Quality checklist
- Does each case file have all seven fields, with the mistakes field filled?
- Is the file anonymised and stored under a code, with the key kept separately?
- Is the index row tagged, including for failed projects?
- Before this project, were all close cases read, including contradicting ones?
- Does every claim taken from cases state how many cases it rests on?
- Is each transferred lesson written as a hypothesis with a planned check?
- Was an outside source or a test used where the decision depends on the lesson?

## Notes for Uzbekistan
- Practical caution: in a small business community a client can be recognised from category, city and size alone; anonymise more strongly than seems necessary and ask the client before reusing anything outside the agency.
- Tag Tashkent and regional work separately and treat a lesson from one as a hypothesis for the other.
- Keep quotes in files in the original language, Uzbek or Russian, with a translation beside them.
- Bot-survey cases describe the people the bots reached, who may under-represent older and rural people; note this limit in each such file.
- Polite reporting hides errors. Ask each team member for one mistake per project so the mistakes field is never empty.
