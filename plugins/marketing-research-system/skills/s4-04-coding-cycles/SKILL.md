# First-cycle and second-cycle coding methods (S4-04)

A code is a word or short phrase that assigns a summarising or essence-capturing attribute to a piece of data. Johnny Saldana's The Coding Manual for Qualitative Researchers (Sage; first edition 2009, later editions since) organises coding into two cycles. First-cycle methods are applied when the data are first labelled; the manual profiles about thirty of them in groups (grammatical, elemental, affective, literary and language, exploratory, procedural). Second-cycle methods reorganise first-cycle codes into categories, themes or concepts. This skill covers the five first-cycle methods most useful for marketing interviews (in vivo, process, emotion, versus, values) and one second-cycle method (pattern coding).

Evidence grade: B. Grades are A = tested in peer-reviewed research, B = established professional standard, C = practitioner tool with little formal testing. The manual is a standard reference and its methods are drawn from published research traditions, but the scheme as a whole is a craft repertoire, not a validated instrument. Saldana himself says coding is "primarily an interpretive act". Two careful coders can code the same passage differently and both be defensible, so put weight on the audit trail (codebook, memos, extracts), not on the codes as measurements.

Working rules for the assistant: answer in the user's language (Uzbek, Russian or English). Label FACT (the extract, with ID) versus INTERPRETATION (every code and pattern code). When the code tables are handed over, return to the research-orchestrator skill.

## When to use it / When not to use it
Use it when:
- Transcripts, open answers or field notes exist and nobody has labelled them systematically yet.
- The team wants to choose a coding lens on purpose instead of defaulting to topic labels.
- Another method (S4-01, S4-02, S4-05) needs coded data as input.

Do not use it when:
- The data are a handful of short answers; an affinity sort (S5-01) is enough.
- Categories are fixed in advance and must be counted (S4-21).
- The team expects codes to be the findings. Codes are a step; findings answer the research question.

## What you need before starting (inputs)
1. The research question. It decides which coding methods fit.
2. Data in the original language, segmented into answers or passages, each with respondent ID.
3. Who will code: one person or a team. A team needs a shared codebook and one codebook editor.
4. Time for at least two passes (Saldana's point is that the first cycle is rarely right and recoding is normal) and a memo file.

## Procedure
1. Match method to question. Ask the user: "What do we most need to see: their words, what they do, what they feel, what they are torn between, or what they believe?" Then choose one or two first-cycle methods (two is a working rule to keep passes manageable):
   - In vivo: the respondent's own word or phrase becomes the code. Use to keep customer language and avoid imposing the team's framing; pick phrases that are salient or surprising. Process: gerund codes for actions and interactions ("comparing prices", "asking a neighbour"). Use for sequences, change over time, decision routes.
   - Emotion: labels the emotion the respondent recalls or shows, or that the coder infers. Use for decisions, risk, relationships, sensitive topics; mark whether stated or inferred (working rule). Versus: labels a binary conflict between people, groups, ideas or processes as X VS Y. Use when respondents describe tensions, trade-offs or opposing camps.
   - Values: labels values, attitudes and beliefs. Prefix V:, A: or B: so the three stay separate (working convention).
2. Pre-code. Read each transcript once and mark striking quotes. Do not assign codes yet.
3. First-cycle coding. Code passage by passage. Decide lumping versus splitting: one broad code per long passage is fast but can be shallow; many fine codes give nuance but can swamp the analyst. Saldana advises beginners to code more of the data, not less, and to mark truly irrelevant passages N/A. A passage may carry more than one code.
4. Build the codebook as you go: code name, short definition, when to use and when not, one example extract with ID. In a team, the editor adds and merges codes; coders do not invent private variants.
5. Write analytic memos after each session: why a code was chosen, a link noticed between codes, a doubt, a possible pattern. Memos record how the reasoning developed and can themselves be coded later.
6. Check the first cycle. Recode the first two transcripts after finishing the last one, because code meanings drift (working rule). Solo coders should show excerpts and codes to a colleague. Teams that want a number can compute agreement; Saldana reports that some researchers cite 85-90 percent as a minimum while others rely on group consensus. State which route was used.
7. Transition. List all codes. Merge duplicates, split overloaded codes, drop codes used once that add nothing (keep them in a parked list). Lay codes out by similarity before pattern coding; Saldana calls this code mapping.
8. Second cycle, pattern coding. Group similarly coded data under a pattern code: a meta-code that names a theme, an explanation, a relationship or a construct. For each pattern code write: its name, the first-cycle codes it gathers, a one-sentence rule for what belongs, and extracts from several respondents. Decision rule (working rule): a pattern code needs support from more than one respondent and more than one first-cycle code; otherwise it is still a first-cycle code with a grander name.
9. Move up one more level only if needed. Saldana's model runs from codes to categories to themes or concepts to assertions. A theme is an outcome of analysis, written as a phrase or sentence, not a label applied during coding. His example: SECURITY is a code; "a false sense of security" is a theme. Keep the number of final themes small.
10. Hand over the codebook, the coded extracts, the pattern codes and the memo log to the next method, and state the limits. Then return to research-orchestrator.

## Worked example
INVENTED EXAMPLE - not real data. A housing developer in Tashkent interviewed 10 recent flat buyers. Question: what makes buyers hesitate before paying the deposit? Methods chosen: in vivo plus versus for all data, emotion on the hesitation passages.
Input:
```
R4: "Ota-onam 'tayyor uyni ol' deydi, men esa bo'lib to'lashga faqat
     qurilayotganiga yetaman."                                          FACT
R6: "Ходил на стройку каждую неделю, пока не увидел третий этаж."       FACT
```
Output:
```
R4  in vivo: "tayyor uyni ol"
    versus: PARENTS' ADVICE VS OWN BUDGET
    emotion: torn (inferred)                                        INTERP
R6  in vivo: "пока не увидел третий этаж"
    process: visiting the site weekly
    emotion: distrust easing (inferred)                             INTERP
Pattern code: SEEING BEFORE PAYING
  gathers: visiting the site weekly | "пока не увидел..." |
           asking earlier buyers | FINISHED VS PROMISED
  rule: any act of checking physical progress before a payment
  support: R1, R2, R4, R6, R9 (5 of 10)                             INTERP
Memo: versus codes cluster around family advice; possible second
  pattern, only R4 and R8 so far - not yet a pattern code.
```

## Common mistakes
- Using only descriptive topic labels ("price", "location"), or choosing a coding method by habit instead of by research question.
- Translating or tidying in vivo codes, which removes the reason for using them.
- Recording inferred emotions as if the respondent had stated them.
- Forcing every passage into an X VS Y when no conflict is described; mixing values, attitudes and beliefs in one code.
- Stopping after the first cycle and presenting a code list as findings, or pattern codes that are only folder names for a topic.
- No codebook or memos, so code meanings drift and nobody can reconstruct why codes were merged.

## Quality checklist
- Is the choice of coding methods justified by the research question?
- Does every code in the codebook have a definition and an example extract with ID?
- Are in vivo codes verbatim and in the original language, and inferred emotions marked as inferred?
- Was the first cycle revisited and recoded at least once?
- Does each pattern code gather several first-cycle codes from several respondents, with a stated inclusion rule?
- Do dated memos exist, and is it stated how coding was checked (colleague review, consensus or agreement figure)?

## Works with
- S1-04 in-depth interviews and S1-07 JTBD switch interviews: produce the data; S3-11 interview snapshot supports pre-coding.
- S4-01 thematic analysis: these code types serve its coding phase; pattern codes become candidate themes.
- S4-02 grounded theory coding: in vivo and process codes are its usual open codes; the manual lists focused, axial and theoretical coding as second-cycle methods.
- S4-03 abductive analysis: versus codes and odd in vivo phrases are good places to look for surprises. S4-05 matrix displays: pattern codes can become the columns of a respondent-by-theme matrix.
- S4-21 content analysis: use instead when a fixed frame must be counted. S5-01 affinity diagram and S5-02 insight ladder: take pattern codes forward into synthesis.

## Notes for Uzbekistan
- In vivo codes stay in the language and script the respondent used. Do not merge an Uzbek phrase and a Russian phrase into one in vivo code because they translate alike; link them at the pattern-code stage.
- Agree one convention for process codes in each working language (Uzbek verbal noun in -ish, Russian verbal noun or infinitive) so the code list sorts cleanly.
- Emotion coding from transcripts is weak when respondents answer politely or agree by habit. Code stated emotions only when tied to a concrete episode, and mark the rest as inferred or leave them uncoded.
- Versus codes about family, elders or business partners may be voiced indirectly. Code the conflict only when the text supports it and note the indirect wording in a memo. Tag every transcript with place (Tashkent or region) and channel so pattern codes can be checked by group.
- Open answers from Telegram bots are short; lump rather than split, and remember the sample is likely to miss older and rural people. Saldana's examples come from Western, mostly US, research settings. His emotion and values vocabularies are starting points, not a fixed list.
